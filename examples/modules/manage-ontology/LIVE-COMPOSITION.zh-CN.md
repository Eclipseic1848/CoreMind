# 用真实服务验收资料整理助手

业务方可以用两份独立资料目录和两个记忆主体检查资料引用、偏好、Skill、文件工具及可选本体。每次输入均为合成资料。维护者可从隔离的本地工程运行以下案例。

## 准备

1. 采用 [document-assistant 模板](../../../packages/coremind-templates/templates/general/document-assistant/README.md)创建两个项目。甲使用[资料室清单](document-assistant-corpora/archive/manifest.json)，乙使用[蓝签清单](document-assistant-corpora/blue/manifest.json)。为两个项目分别创建知识读者凭据和知识状态文件。每份清单与同目录下的 `sources/` 一起分发。
2. 按[知识服务示例](../manage-knowledge/README.zh-CN.md)用 BGE-M3 建立两套 Qdrant 索引。按[记忆服务示例](../manage-memory/README.zh-CN.md)建立两个 Hindsight 个人记忆库，各有独立读者和管理凭据。宿主执行确认与更正，智能体只获得当前主体的读者凭据。
3. 在两个项目中选择获准处理合成资料的模型，填入各自的服务地址。甲项目另运行 `node enable-ontology.mjs`，把生成的配置接到 [document-review 模型](models/document-review/model.ttl)的只读本体服务。写摘要所需的文件权限限本项目。模型不接收记忆管理和本体执行令牌。

## 案例

| 顺序 | 宿主操作与新任务 | 可独立核查的结果 |
| --- | --- | --- |
| 甲一 | 保持偏好库为空。比较《资料室手册》的两个版本，把有出处的新增项写到 `summary.md`。 | 新增“归还后核销”，依据为 `guide-v2.md` 第 1 行，对照为 `guide-v1.md` 第 1 行。 |
| 甲二 | 宿主确认“整理资料摘要时优先使用 Markdown 表格”。用本体配置启动新会话，整理《新制度草稿》，检查 `urn:doc:draft` 的 `publish` 前置条件。 | 摘要写明“档案交接登记”是本周新增规定。引文应指向 `draft-v1.md` 第一版第 3 行，列名在第 1 行。草稿缺少已复核状态，发布检查拒绝。 |
| 乙一 | 用乙目录与凭据，确认“整理资料摘要时优先使用带编号清单”。运行与甲一相同的任务。 | 编号清单写出“蓝签复核”，依据为 `blue-v2.md` 与 `blue-v1.md` 第 1 行。甲的资料和偏好均不可见。 |
| 甲三 | 宿主通过 `correct` 把甲的偏好更正为项目符号清单，重启记忆网关，重新启动知识服务并指定 `--withdraw guide:2`。在新会话重复甲一。 | 摘要使用清单并说明只剩一版，`guide-v1.md` 可引用。旧版引文可查为已撤回。撤回的正文不得作为结论依据。 |

普通配置使用 `coremind.yaml`。检查发布条件时改用 `coremind-ontology.yaml`。CLI、TypeScript、Python 同步和异步命令见模板说明。要在同一业务目录中启动有独立身份的持久会话，可在源码根目录运行下面的命令。

```sh
node examples/modules/manage-ontology/live-document-session.mjs ./project-a/coremind.yaml "按已确认偏好比较《资料室手册》两个版本，附文件名、版本和行号，用 write 保存到 summary.md。"
```

每次调用新建会话 ID。检查输出的会话 ID、运行 ID、工具成功回执和工程中的 `summary.md`。下一个案例会使用同名输出文件，先保留上一份摘要。真实服务地址、模型和凭据均由当前业务工程提供。

## 恢复与隔离

- 分别用另一项目的知识读者访问当前服务，应拒绝。同一知识服务中，越出范围和失效的引文查询均返回 `unknown`。记忆管理员跨主体操作应返回 403，召回只含自己的主体与有效版本。
- 给目录增加超出模型单块长度的新条目，记录重建失败后的状态摘要。移除测试条目再启动，有效版本和撤回回执应与故障前一致。
- 停止知识服务，再次启动资料任务，核对模型请求次数与输出文件。取消正在等待模型的请求，核对运行结果和输出文件。对外部动作则单独核查业务数据库实际写入次数与返回给智能体的回执，见[动作验收](README.zh-CN.md)。

## 2026-11-24 Windows 开发验收

环境为 Windows 11、Intel Core Ultra 9 285H、31.5 GiB 内存。知识服务使用 Qdrant Client 1.15.1 的内存索引和 BGE-M3 ONNX INT8，记忆使用 Hindsight 1.2.3 和 PostgreSQL 18.1。草稿校验使用 RDFLib 7.6.0、pySHACL 0.40.2。合成任务经过真实 Qwen3.8-27B 推理。两个工程依次启动自己的知识服务，分别保存资料和状态，使用各自读者令牌。Hindsight 同时保存两个主体的个人记忆。

| 度量 | 本机观测 |
| --- | --- |
| 初次启动至就绪 | 知识服务 7.59 秒，记忆网关 3.79 秒，本体 3.82 秒，Hindsight 在启动后 23.36 秒观察到就绪。 |
| 查询 | 通过已认证知识 MCP 重复查询同一问题 10 次，P50 为 33.86 ms，最近秩 P95 为 69.12 ms。 |
| 索引 | 另测 5 份 Markdown 资料、6 个块。模型加载 2.59 秒，建空索引并编码、写入全部资料 0.15 秒。 |
| 进程内存 | 每 250 ms 采样一次服务进程树的工作集。Hindsight 最高 1247.3 MiB，知识 1098.4 MiB，记忆网关 111.3 MiB，本体 77.8 MiB。各服务单独计数。 |

甲一、甲二、乙一、甲三分别由 CLI、TypeScript、Python 同步、Python 异步入口交付了摘要。另用三个独立 ChatSession 验证无偏好、已确认表格及更正为清单后的输出。原题的 TypeScript 与 ChatSession 最后分别用时 45.73 秒和 41.70 秒，各向模型发送 4 次请求，写出相同的登记规定、第 3 行引文和禁止发布的依据。[逐次运行、实际摘要、会话回执及完整哈希](live-composition-results.json)

历史失败包括同轮串行工具争用、Qwen 思考输出耗尽 900 token、单文档任务重复检索触发 15 次工具上限，以及把资料行误称为标题。修复后按原题和原预算复验。检索和引文解析两项工具均返回第 3 行原文及第 1 行表头。首次评分把“第 3 行（表头见第 1 行）”误判成“第 3 行是表头”。复核同一份输出并用两份旧错误摘要作对照后，两份新摘要通过。业务工程输出采用 LF（1034 字节），Windows 存档副本采用 CRLF（1057 字节），验收记录分别列出其字节哈希。

两个项目互用知识令牌分别返回 401，跨主体管理记忆返回 403。更正后重启能读回新偏好。无效增量使真实索引构建失败，状态文件摘要相同。停止知识服务后重试产生零个模型请求。在已收到模型响应头时取消，运行记录为 `aborted`，无写工具调用，旧文件字节相同。另用合成 SQLite 动作处理器在成功提交后丢弃回执，原请求为 `unknown`，重复请求和更换请求 ID 后数据库总共仍只有一笔。

CLI 验收在临时目录对写工具作非交互预批准。SDK 示例把批准范围限定到本项目的 `summary.md`。Python 使用工作区构建的 Node Worker。正式候选和公开安装包的验证由发布阶段执行。样本均为小型合成资料，内存数据不含独立 PostgreSQL、模型服务器及宿主 SDK 的占用。
