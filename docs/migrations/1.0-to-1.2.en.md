# Migrating from 1.0 to 1.2

[简体中文](1.0-to-1.2.zh-CN.md)

This page describes migration boundaries on the 1.2 development line, not a completed release. When upgrading from 1.0, also follow the existing requirements in [Migrating from 1.0 to 1.1](1.0-to-1.1.en.md). Keep all CoreMind npm packages, the Python SDK, and its bundled Worker on the same release. This section covers the project script loading trust introduced in 1.2.

## Project script loading trust

Configured script tools are imported during Runtime creation. Module top-level code and transitive dependencies execute with host process privileges. Before any configured entry is imported, the host must explicitly approve the complete batch. Missing approval, denial, and callback failures reject with `execution_security_violation`; cancellation retains `aborted`. Configurations without project scripts require no decision. Missing script files may retain their previous warning-and-skip behavior; files appearing later cannot acquire approval implicitly.

TypeScript hosts use `approveProjectCode(request, signal)`. The request includes the canonical project directory, sorted and deduplicated entry paths, entry SHA-256 values, and a batch fingerprint. The batch covers effective inherited, independent, and deferred tools of every Agent actually constructed. Each import checks the entry again. Return `true` only for code the host has reviewed:

```ts
const runtime = await CoreMindRuntime.create({
  config,
  configDir,
  approveProjectCode: async (request) => approvedFingerprints.has(request.fingerprint),
});
```

CLI `run`, `chat`, and `eval` share this decision. TTY prompts default to rejection, including empty input, EOF, and cancellation. Prompts go to stderr. Decisions are reused only for the same complete fingerprint in the current command process. Non-TTY input is never consumed as approval: explicitly pass `--trust-project-code` or `--trust-project-code=true` for reviewed code. `false` denies; other values are argument errors. `--permission full` does not approve imports. `doctor` and `check` remain static and do not import project scripts.

Both Python clients accept the boolean-only keyword `trust_project_code: bool = False`. Set it to `True` only for reviewed projects. Standard Worker v1/v2 initialize accepts `trustProjectCode` and advertises `projectCodeTrust`. The new SDK requires this capability before run/chat or callable registration, even with the default `False`; it cannot silently downgrade to an older Worker. Upgrade custom Workers alongside the SDK, and generate the v2 fingerprint and bundled Worker together. The single v1 tool-discovery challenge retry retains the original trust field.

Approval of loading grants no tool, file, network, credential, or Child permissions. Tool approval, explicit deny, workspace restrictions, and recovery gates remain active. Entry hashes do not prove immutable transitive dependencies or prevent a host-privileged external process from replacing files after checks; this is not an OS sandbox. Host-loaded extension and callable objects do not trigger duplicate approval. Direct calls to low-level `loadScriptTool()` or `buildTools()` mean the caller already trusts the specified code and do not replace configuration-driven Runtime approval.
