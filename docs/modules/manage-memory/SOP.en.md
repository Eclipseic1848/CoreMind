# Long-term memory development SOP

Prepare at least two projects, two subjects, two agents, and two session branches. Record the Hindsight and optional model versions, along with the evidence, storage, and access scope used for the check. Run the following cases with synthetic inputs.

| Case | Verify |
| --- | --- |
| M01 Event retry | Submit the same bank, document ID, expected revision, and content concurrently, then replay after restart. Verify that only one active memory exists and that different input for the same document operation revision is rejected. |
| M02 Scope | Try a new session for the same subject and repeat with another project, subject, agent, and a branch without a grant. The authorized new session can recall. Out-of-scope search and administration by ID fail. |
| M03 Candidate extraction | Use two runs with different outcomes and propose a candidate with evidence, applicable conditions, and a counterexample. Verify absence before approval, visibility after approval, and absence after withdrawal. Test both an empty bank and a bank that contains related material but lacks a fact the question needs. Verify that the service withholds a candidate in both cases. |
| M04 Correction | Change the table preference to a list preference. Check that a new session only recalls the new value, and that a stale revision cannot overwrite it. Inject a storage failure and verify that the call reports failure and the old content never appears as a new revision. |
| M05 Expiry and forgetting | Expire a memory under a test clock. After forgetting, inspect storage, indexes, and read paths. Restart, search again, and replay the original event. Check the deployed backup policy for deletion replay on restore. |
| M06 Entry point parity | Search through CLI + YAML, the TypeScript SDK, and the synchronous and asynchronous Python SDKs. Compare the same fact and revision under the same scope. Disconnect the service and check the error. The agent should avoid substituting historical information for a current memory. |
| M07 Direct calls and Agent binding | Use the [empty Python project example](../../../examples/modules/manage-memory/README.en.md#recall-directly-from-an-empty-python-project) to call the standard MCP `recall_memory` tool, then bind the same endpoint and reader token to a CoreMind Python Agent. Compare bank, document ID, revision, text and source. Verify HTTP 401 with an invalid token and an empty result with a reader whose own bank is empty. Record a call failure when the dedicated gateway stops, then remove the binding and confirm the Agent runs with zero memory tool calls. |

Run the checks in the [module manifest](module.yaml) and `npm run check:modules`. Record the result, entry point, and failure stage for each case. When using a deterministic candidate fixture, report lifecycle behavior and live model extraction quality separately.

Use the [automated acceptance for direct knowledge and memory calls](../manage-knowledge/SOP.en.md#automated-acceptance-for-direct-knowledge-and-memory-calls) to rerun M07 with the actual Hindsight gateway and both reader tokens. The script supplies the checks and model fixture.

## Verify standalone deployment and upgrades

1. Run `python -m pip install coremind-memory-mcp==0.1.0` in a dedicated Python 3.12 environment and verify `coremind-memory-mcp --version` reports 0.1.0. The compatibility baseline is Hindsight API/client 1.2.3 and PostgreSQL 18.1. Verify other versions in the target environment. In a separate empty project, use only a reader token and a standard MCP client. `tools/list` must expose just `recall_memory`. Write a fact through the host and query it through MCP. Check bank, document ID, revision, text and source. `/health` checks only the gateway process.
2. Run M01–M07. A missing or invalid reader token returns HTTP 401. A valid administrator targeting an ungranted bank gets 403. Exercise the published CLI, TypeScript SDK, and synchronous and asynchronous Python SDKs. All four callers resolve installed dependencies from the clean consumer. Python uses its bundled Worker. Use `acceptance.mjs` to compare the bank, document ID, revision, text and source across the four results.
3. Record the gateway source release, Hindsight client/API versions, PostgreSQL version, bindings and receipt path. 0.1.0 uses the 2.0.0 receipt JSON, owned by one gateway process. Before upgrading, stop writes and back up PostgreSQL and the latest receipts. In an isolated copy, test an active fact, a forgotten fact, replay of its deletion, a stale correction and recall after restart with the same reader. On rollback, restore the previous software and consistent state, retain the newest forgetting receipts and replay those deletions. When switching from the 2.0.0 scripts to the 0.1.0 wheel, retain the original `--state` and host bindings. After restoring old PostgreSQL data, load the latest receipts and replay forgetting before admitting readers. To disable memory, remove the tool from the application, revoke its reader token and stop the gateway. Retain the database and receipts under the host retention policy.

## Standalone gateway 0.1.0 verification

On 2026-11-25 a clean Windows Python 3.12 environment installed the wheel and connected to isolated Hindsight 1.2.3 and PostgreSQL 18.1. The gateway read a version 1 receipt written by the 2.0.0 scripts without rewriting it. CLI/YAML, TypeScript and both Python entry points used installed 2.0.0 packages and returned identical memory and source. Checks covered two subjects, idempotent retention, correction conflicts, expiry and forgetting. After rolling back to the old scripts, only authorized facts remained visible. Restoring an old database brought back one deleted native document. The latest receipt hid it, and replaying the deletion twice removed it from native storage while the control remained readable. Reflect used real Hindsight with a deterministic local model fixture to verify that publishing an experience requires host confirmation.

## P2-B verification record

- Hindsight OSS 1.2.3 and PostgreSQL covered writes, restart, correction, expiry, deletion, scope isolation, and recall through the four entry points. All eight memory service unit tests passed.
- The same five synthetic questions were rerun with `deepseek-flash` after tightening the direct evidence requirement. All three questions with direct evidence produced candidates for review. Neither of the two questions without direct evidence produced a candidate.
- With Hindsight automatic observations enabled for a separate check, deleting the source removed derived observations and orphaned entities. A control record in the same bank remained available. Automatic observations remain off by default.
- After logical PostgreSQL restore, current forgetting receipts blocked the restored content. Replaying the deletion twice left zero target documents, memory units, and native recall hits. The control record remained available. Verify physical backups, point-in-time recovery, backup media cleanup, and production scale in the deployment environment.
