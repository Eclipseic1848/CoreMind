# 长期记忆开发 SOP

准备至少两个项目、两个主体、两个 Agent 和两个会话分支。记录 Hindsight 和可选模型的版本，以及本次验证使用的资料、存储和访问范围。用合成输入执行下列用例。

| 用例 | 如何验收 |
| --- | --- |
| M01 事件重试 | 并发提交同一记忆库、文档标识、预期版本和内容，再重启重放。检查只出现一条活动记忆，相同文档操作版本对应不同输入的请求被拒绝。 |
| M02 作用域 | 分别用同一主体的新会话、其他项目、其他主体、其他 Agent 及未获授权的分支测试。授权的新会话可召回。越权查询和按 ID 执行的管理操作均失败。 |
| M03 候选提炼 | 选两次有不同结果的任务，从指定证据提炼带适用条件和反例的候选。确认前召回为空，确认后可见，撤回后不可见。分别用空记忆库和有相关资料但缺所问关键字段的请求验证拒答。检查相近主题没有被写成替代候选。 |
| M04 更正 | 将表格偏好改为清单。检查新会话只召回新值，过时版本的写入请求被拒绝。注入一次存储错误，核对调用明确失败，旧版本不会作为新版本返回。 |
| M05 到期与遗忘 | 让一条记忆在测试时钟下到期。执行遗忘后检查存储、索引和读取路径，重启后查询并重放原事件。按实际部署的备份方案核查是否需要在恢复时重放删除记录。 |
| M06 入口一致性 | 从 CLI + YAML、TypeScript SDK、Python 同步及异步 SDK 查询。同一范围看到相同事实和版本。断开服务并观察失败结果，核对 Agent 不会用历史数据替代当前记忆。 |
| M07 业务代码直调与 Agent 绑定 | 用[空白 Python 项目示例](../../../examples/modules/manage-memory/README.zh-CN.md#从空白-python-项目直接召回)先调用标准 MCP 的 `recall_memory`，再把同一地址和读令牌接入 CoreMind Python Agent。比对记忆库、文档 ID、版本、正文和来源。用无效令牌复查 HTTP 401，用另一个主体自己的空库验证返回为空。停止专用网关时记录调用失败，移除绑定后验证 Agent 仍可运行且记忆工具调用数为零。 |

运行[模块清单](module.yaml)登记的检查和 `npm run check:modules`。记录每个用例的观测结果、入口和失败阶段。使用固定候选夹具时，将生命周期结果和真实模型的提炼质量分别记录。

复跑 M07 时使用[知识与记忆直调自动验收](../manage-knowledge/SOP.zh-CN.md#知识与记忆直调自动验收)，传入真实 Hindsight 网关及两组读令牌。用例目录和模型夹具由脚本准备。

## 验收独立部署与升级

1. 在专用 Python 3.12 环境运行 `python -m pip install coremind-memory-mcp==0.1.0`，再运行 `coremind-memory-mcp --version` 确认为 0.1.0。兼容基线为 Hindsight API/客户端 1.2.3、PostgreSQL 18.1。其他版本由部署方复验。在另一个空白项目仅使用读令牌和标准 MCP 客户端，确认 `tools/list` 只列出 `recall_memory`。由宿主写入一条事实，再经 MCP 核对记忆库、文档 ID、版本、正文和来源。`/health` 只检查网关进程。
2. 逐项执行 M01–M07。无有效读令牌返回 HTTP 401，有效管理员访问未获授权的库返回 403。使用公开安装的 CLI、TypeScript、Python 同步和异步入口。Python 沿用 wheel 内置 Worker，四个调用端均从空白项目解析本地依赖。使用 `acceptance.mjs` 对照四份结果的记忆库、文档 ID、版本、正文和来源。
3. 记录网关源码发布版、Hindsight 客户端/API 版本、PostgreSQL 版本、绑定及回执路径。0.1.0 沿用 2.0.0 的回执 JSON，每个文件由一个网关进程独占。升级前暂停写入并备份 PostgreSQL 和最新回执。在隔离副本验证已生效事实、已遗忘事实、重放遗忘、旧版本更正冲突及相同读者重启后的召回。回滚时恢复上一版本程序和一致的状态，保留并重放升级后新增的遗忘回执。从 2.0.0 切换到 0.1.0 时使用原 `--state` 和宿主绑定，恢复旧 PostgreSQL 后先读最新回执、重放遗忘再对业务开放。停用时从业务配置移除读工具、撤销读令牌并停止网关，按宿主保留策略保管数据库和回执。

## 原生部署与恢复演练

在新的目录运行[独立部署演练](../../../examples/modules/manage-memory/deployment/README.zh-CN.md)。依次确认 PostgreSQL、Hindsight 就绪及真实 MCP 召回。暂停写入后备份数据库及同一时点的回执。恢复到空库并加载最近回执，先检查遮蔽，再重放遗忘并核对原生文档及其派生记忆已清理。网关回退和重新升级前后复查对照事实。保留备份摘要、耗时及具体环境。

## 独立网关 0.1.0 验证记录

2026-11-25 在 Windows 空白 Python 3.12 环境安装 wheel，并单独运行新建的 Hindsight 1.2.3 与 PostgreSQL 18.1。2.0.0 旧脚本写入的版本 1 回执被原样读取。CLI/YAML、TypeScript、Python 同步与异步入口通过已安装的 2.0.0 SDK 查询，四者返回相同的记忆及来源。测试覆盖两个主体隔离、幂等写入、更正冲突、到期和遗忘；回滚旧脚本后仍只返回获准事实。实际恢复的旧数据库含一条已遗忘文档，网关使用最新回执将其隐藏，两次重放遗忘后原生文档数为零，对照文档仍可召回。Reflect 调用真实 Hindsight 与本地确定性模型夹具，验证待确认候选经宿主确认才成为经验。

## P2-B 验证记录

- Hindsight OSS 1.2.3 与 PostgreSQL 环境已覆盖写入、重启、更正、到期、删除、作用域隔离及四入口召回。记忆服务单测 8 项通过。
- `deepseek-flash` 使用同一组 5 道合成题复验直接证据准入。有直接证据的 3 题均生成待确认候选，缺少直接证据的 2 题均未生成候选。
- 单独启用 Hindsight 自动观察后，删除源文档会清理派生观察及其孤立实体，同库对照记录仍可召回。默认仍关闭自动观察。
- PostgreSQL 逻辑还原后，最新遗忘回执阻断恢复出的旧内容。重放遗忘两次后目标文档、记忆单元及原生召回均为空，对照记录保留。物理备份、时间点恢复、备份介质清理及生产规模需按部署环境验证。
